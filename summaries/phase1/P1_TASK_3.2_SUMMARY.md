### 2. Created ReferralLink Model
**File:** `referrals/models.py`

**Model:** `ReferralLink`

**Fields:**
- `created_by` (ForeignKey to User) - Admin Pandit or Super Admin who generated the link
- `token` (CharField, unique) - Unique token used in URL path
- `referral_code` (CharField, unique) - Hexadecimal code that must match token
- `max_uses` (PositiveIntegerField, default=5) - Maximum number of uses
- `used_count` (PositiveIntegerField, default=0) - Current usage count
- `is_active` (BooleanField, default=True) - Active status
- `created_at` (DateTimeField, auto_now_add) - Creation timestamp
- `updated_at` (DateTimeField, auto_now) - Last update timestamp
- `expires_at` (DateTimeField, nullable) - Optional expiry date

**Model Methods:**
- `is_expired()` - Check if referral link is expired
- `can_be_used()` - Check if referral link can be used for new registration

**Constraints:**
- `token` is unique and indexed
- `referral_code` is unique and indexed
- `max_uses` has validators (MinValueValidator(1), MaxValueValidator(100))
- `created_by` uses `on_delete=models.PROTECT` (never delete referral data)

**Indexes:**
- Index on `token`
- Index on `referral_code`
- Index on `created_by` and `is_active` (for filtering)

**Purpose:**
- Represents a referral link generated by Admin Pandit or Super Admin
- Supports limited-use referral links (max 5 uses)
- Tracks usage count and expiry
- Provides audit trail of referral generation

---

### 3. Created ReferralUsage Model
**File:** `referrals/models.py`

**Model:** `ReferralUsage`

**Fields:**
- `referral_link` (ForeignKey to ReferralLink) - The referral link that was used
- `referred_pandit` (ForeignKey to User) - The Pandit who registered using this link
- `used_at` (DateTimeField, auto_now_add) - When the link was used

**Constraints:**
- `unique_together` on `referral_link` and `referred_pandit` (one Pandit can only use one link once)
- Both foreign keys use `on_delete=models.PROTECT` (never delete referral data)

**Indexes:**
- Index on `referral_link` and `used_at` (for audit queries)
- Index on `referred_pandit` (for trust chain queries)

**Purpose:**
- Tracks each usage of a referral link
- Provides complete audit trail
- Supports abuse prevention
- Enables trust verification

## Why Referral Data is Separated from User

### 1. Separation of Concerns
**Why:**
- User model is for identity and authentication
- Referral data is for onboarding and trust chain
- Mixing them would pollute the User model

**Benefits:**
- Clean, focused models
- Easy to understand and maintain
- Clear data ownership

---

### 2. Audit Requirements
**Why:**
- Referral data must be preserved permanently (audit requirement)
- User model changes should not affect referral audit trail
- Separate models ensure audit data integrity

**Benefits:**
- Complete audit trail
- Easy to query referral history
- Compliance with audit requirements

---

### 3. Moderation & Governance
**Why:**
- Admin needs to view referral audit data separately
- Referral management is a distinct feature
- Separation makes moderation easier

**Benefits:**
- Easy to query referral links
- Easy to track usage
- Easy to identify abuse patterns

---

### 4. Scalability
**Why:**
- Referral data can grow independently
- User model remains lightweight
- Better database performance

**Benefits:**
- Better query performance
- Easier to optimize
- Scales better with growth

---

### 5. Data Integrity
**Why:**
- Referral relationships are immutable (audit requirement)
- User model may need different deletion policies
- Separation prevents accidental data loss

**Benefits:**
- `on_delete=models.PROTECT` on referral models
- Prevents accidental deletion
- Maintains audit trail integrity

---
